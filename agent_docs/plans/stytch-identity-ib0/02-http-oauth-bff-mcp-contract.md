# 02 — Candidate Identity HTTP, OAuth, BFF, and MCP contract

## Common HTTP and metadata rules

Production uses HTTPS. Authorization, broker, callback, token, revoke, logout, and all OAuth error responses send `Cache-Control: no-store`, `Pragma: no-cache`, and HSTS; token/revoke responses additionally send `X-Content-Type-Options: nosniff`. OAuth JSON is `application/json;charset=UTF-8`; local browser errors are `text/html;charset=UTF-8`. Duplicate form/query names are rejected, including duplicate `resource`, `state`, `code`, `code_verifier`, client-auth fields, or PKCE fields. Invalid UTF-8, controls, unexpected JSON fields, and limits fail before state change. Form endpoints accept exactly `application/x-www-form-urlencoded`; no CORS is enabled on token/revoke.

`GET /.well-known/oauth-authorization-server` is the RFC 8414 metadata endpoint only when the configured issuer has no path. For issuer `https://host.example/issuer/path`, the endpoint is exactly `https://host.example/.well-known/oauth-authorization-server/issuer/path`; the returned `issuer` is byte-for-byte the configured issuer. Metadata contains exact absolute `authorization_endpoint`, `token_endpoint`, `revocation_endpoint`, and `jwks_uri`; `response_types_supported:["code"]`; `response_modes_supported:["query"]`; `grant_types_supported:["authorization_code","refresh_token","client_credentials"]`; `code_challenge_methods_supported:["S256"]`; `token_endpoint_auth_methods_supported:["none","client_secret_basic","private_key_jwt"]`; `token_endpoint_auth_signing_alg_values_supported:["ES256"]`; `revocation_endpoint_auth_methods_supported:["none","client_secret_basic","private_key_jwt"]`; `revocation_endpoint_auth_signing_alg_values_supported:["ES256"]`; stable sorted exact `scopes_supported`; and `authorization_response_iss_parameter_supported:true`. It omits registration and introspection endpoints. It is 200, ≤32KiB, `application/json;charset=UTF-8`, `Cache-Control: public,max-age=300`, and an ETag; matching `If-None-Match` is 304 with no body.

`GET /.well-known/jwks.json` is 200, ≤64KiB, `application/jwk-set+json`, ETag/cacheable; it contains only public P-256 ES256 signing keys with unique `kid`, `use:"sig"`, and `alg:"ES256"`.

## Authorization request and recoverable state

Required, exactly once: `response_type=code`, `client_id`, `redirect_uri`, `resource`, `audience`, nonempty allowed `scope`, `state`, `code_challenge`, `code_challenge_method=S256`. `redirect_uri`, resource absolute URI, and single audience match one enabled registration exactly; no default/wildcard/prefix/normalization/Host-derived choice. State is 1..1024 raw bytes. The verifier is 43..128 characters from RFC 7636 unreserved `[A-Za-z0-9-._~]`; challenge is unpadded base64url SHA-256 of verifier. Any duplicate, plain method, padding, invalid character, or mismatch fails.

Authorize persists a 10-minute `broker_transactions` row with state HMAC lookup/replay protection and the exact `state-seal-v1` AES-256-GCM envelope frozen in `03-data-state-and-revocation.md`. Its AAD is byte-framed, not delimiter-concatenated: ASCII `primer.oauth.state`, byte `0x01`, broker UUID and OAuth-client UUID as 16 raw bytes each, then registered redirect URI, resource URI, and audience in that order, each as a uint32 big-endian byte length followed by strict UTF-8 bytes. State is 1..1024 bytes; each text field retains its registered bound; total AAD is capped at 4287 bytes. The envelope is `0x01 || 12-byte random nonce || ciphertext+16-byte tag`, uses the exact 32-byte key selected by `state_key_version`, and never falls back. Unknown/removed versions, malformed lengths/UTF-8, tamper, or authentication failure fail closed. The original state never appears in logs or plaintext persistence and its in-memory buffer is zeroed at every terminal outcome.

The broker transition is `pending → provider_started → provider_validating → authorized`; it may terminalize from **any nonterminal** to `denied|failed|expired`. Callback decrypts exact state only in memory, then atomically creates code/grant/association, terminalizes and nulls `state_sealed` plus callback authorization artifact. It redirects only after commit and only then returns the exact original state.

## Client authentication and code exchange

Confidential clients use exactly one registered `client_secret_basic` or `private_key_jwt` mechanism; public static MCP clients use `none` plus PKCE. `private_key_jwt` form fields are exactly one `client_id`, `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, and `client_assertion`. Its protected header is `alg=ES256` plus a registered `kid`; `none`, embedded `jwk`, `jku`, `x5u`, and attacker-selected key locations are rejected. Claims are `iss=sub=client_id`, `aud` exactly the **invoked token or revocation endpoint URI**, integral `iat`, integral `exp` with `0 < exp-iat ≤ 5m`, and nonempty bounded `jti`; `nbf` is optional and bounded by the same 60-second clock-skew policy. Verification uses only locally registered active key/JWKS material. A durable `(oauth_client_id,endpoint_kind,jti_hash)` replay insert with TTL through `exp` occurs in the request transaction; collision is `invalid_client`/401. IB1 must STOP if exact active-key resolution and durable replay behavior cannot be qualified.

Authorization-code form requires exactly `grant_type=authorization_code`, `code`, `redirect_uri`, `resource`, `code_verifier`, and `client_id` for public/`private_key_jwt` clients; Basic identifies its client from the Authorization header. Verifier grammar is exactly 43..128 ASCII RFC 7636 unreserved characters. Identity computes unpadded base64url `BASE64URL(SHA256(ASCII(code_verifier)))`, requires an exact 43-character stored challenge and `S256`, and compares in constant time; malformed/mismatch is `invalid_grant`. Code is HMAC-hashed, 60 seconds, one-use, bound to client/redirect/resource/audience/scopes/PKCE/grant/broker transaction. After all checks, Identity signs with an already-ready local in-memory ES256 signer **before** committing the short consume transaction. Signing failure rolls back; commit failure discards token; HTTP response is after commit only. A lost response consumes code and forces browser authorization restart.

Refresh form has exactly `grant_type=refresh_token`, `refresh_token`, `resource`, and optional narrowing `scope`; client authentication follows its registered method. `client_credentials` has exactly `grant_type=client_credentials`, `resource`, and optional narrowing `scope` plus confidential client authentication. Unknown form fields are rejected. Rotation/reuse is IB6 only. `client_credentials` is IB5 only and cannot produce human or publish-confirmation authority.

Token success bodies have exactly the following members (member order is not significant; `scope` is the canonical space-delimited granted scope string): authorization-code human exchange returns `{"access_token":"…","token_type":"Bearer","expires_in":<integer>,"scope":"…","refresh_token":"…"}` with the IB2 initial refresh-family issuance; refresh exchange returns the same five members with the **rotated** `refresh_token`; client-credentials returns only `{"access_token":"…","token_type":"Bearer","expires_in":<integer>,"scope":"…"}` and never a refresh token. No success body contains `id_token`, provider token/session/tuple fields, provider roles, or any unlisted extension member. The fixed invalid-client body is `{"error":"invalid_client"}`.

Revocation accepts exactly `token`, optional `token_type_hint`, and the owning client's registered authentication. Public clients also send exact `client_id`; confidential clients authenticate exactly as at the token endpoint. A valid owned refresh token atomically revokes its family/grant. Unknown, expired, already-revoked, or wrong-owner tokens return the same idempotent 200 empty response and reveal no oracle. Unknown hints are ignored and supported token classes are searched. Offline access JWT revocation is not supported and cannot be made immediately effective; a recognized access-token hint/value still receives the non-oracular 200 while the JWT naturally expires. Database/provider unavailability is 503 and leaves authority unchanged.

## JWT and revocation

Access JWT header is `alg=ES256`, `kid`, `typ=at+jwt`. Claims are exact issuer, human `sub=accounts.id` or service `identity:svc:<id>`, a **single string** audience, registered scope, required signed public `client_id` (`varchar(128)` stable OAuth client identifier from `oauth_clients.client_id`; never an internal UUID), `iat`/`nbf`/`exp` with `exp-iat≤900s`, and random `jti`. `azp` is not used initially and is rejected if present. No provider tuple/session/role, email/profile, product role, workspace, or tenant claim is emitted. Product services validate signature, issuer, one audience, time, scopes, and `client_id` from JWKS and use local membership. Missing, empty, overlong, control-bearing, or non-registered `client_id` is denial. Raw Stytch material never has a fallback path.

## BFF and MCP protected-resource rules

A product BFF creates state+PKCE and its 10-minute pre-auth record, validates state and returned `iss`, exchanges only server-side, and holds the random `__Host-<product>-session` (`Secure; HttpOnly; SameSite=Lax; Path=/`; no Domain) plus encrypted server-side token custody. Mutations use a separate CSRF token and exact Origin/Host allowlist. Browser JS, URL, storage, and browser cookie never receive OAuth/Stytch secrets.

Studio’s RFC 9728 protected resource is the exact `https://<studio-host>/mcp` resource; metadata follows the RFC path-aware well-known rule and names Identity. Its authorization server list, supported header bearer method, and supported scopes are exact registered values. Humans and services authenticate per request and then Studio applies **this authority matrix**:

| Tool class | Human delegated token + active workspace membership | Service token + explicitly granted active service membership |
|---|---|---|
| list/read | allowed | allowed |
| draft create/patch/validate | allowed for author | allowed only with explicit draft scope |
| publish propose/confirm | human only; propose returns a proposal only; confirm uses MRTR when the client supports it | never |

`studio.publish.propose` returns a proposal only and never creates, accepts, or returns `requestState`. Capability negotiation chooses exactly one lane: an MRTR-capable client's initial `studio.publish.confirm` **must** return `InputRequiredResult{resultType:"input_required",inputRequests,requestState}` without publishing; a non-MRTR client receives only the named-UI fallback. The MRTR client retries the **same `studio.publish.confirm` tool/method** with the exact `requestState` plus `inputResponses` and a new JSON-RPC id. Confirmation IDs are nonempty 1..128-byte strict UTF-8 strings without controls; their canonical hash encoding is frozen in `03`. The persisted five-minute state digest binds human subject, public OAuth `client_id` string (`varchar(128)`), workspace, canonical draft digest, and literal tool `studio.publish.confirm`; current authority, validated JWT `client_id` claim, and digest are revalidated and state is atomically consumed exactly once with publish. Studio confirmation records store and compare that public `client_id` string, never an internal OAuth-client UUID. Wrong or missing `client_id` on initial confirm or retry is denial with a sanitized audit field. A same-id retry, any other method, missing/mismatched response, expiry, replay, or binding mismatch fails closed. Expired state is atomically terminalized before replacement state can issue. The named Studio UI fallback never mints, discloses, or accepts MCP `requestState`. No scope/role/test/header bypass is a substitute.
